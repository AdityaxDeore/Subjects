Lab 6: Cloud Security Basics (IAM & Permissions)

Cloud platform: Amazon Web Services (AWS) | Service: IAM (Identity and Access Management) — global service, no region selection needed. IAM itself is free.

Part A — Theory

1. What is IAM (Identity & Access Management) in cloud computing?

Identity and Access Management is the cloud service that controls WHO can access WHAT in a cloud account. It manages digital identities (users, groups, roles) and defines their permissions through policies. IAM handles two jobs: authentication (verifying identity — passwords, access keys, MFA) and authorization (deciding which API actions on which resources that identity may perform). In AWS, IAM is a free, global service and every API call is checked against IAM policies before it is allowed.

2. Why is IAM important for securing cloud resources?

• No shared credentials: every person/application gets its own identity instead of sharing the root account, so access can be granted and revoked individually.

• Least privilege: each identity gets only the permissions its job needs, limiting damage from compromised credentials or mistakes.

• Auditability: every action is logged (e.g., AWS CloudTrail), so you can trace exactly who did what.

• Stronger authentication: MFA can be enforced, and short-lived temporary credentials (roles) replace long-lived keys.

• Without IAM, anyone with the account password would have unlimited power — IAM is what turns one cloud account into a securely shared environment.

3. Difference between users, groups, and roles in IAM.

User: an identity for one person or application, with long-term credentials (password and/or access keys). Example: a developer account.

Group: a collection of users that share the same job function. Permissions are attached to the group once, and every member inherits them — this is how you manage access at scale (e.g., a Developers group) instead of editing each user.

Role: an identity with NO long-term credentials. It is assumed temporarily by a trusted entity — a user, an application on EC2, or another AWS account — which then receives short-lived credentials. Roles are the secure way to grant cross-service and cross-account access (e.g., letting an EC2 instance read from S3 without storing any keys on the instance).

4. What are permissions and policies, and how do they control access?

Permissions are the individual allowed or denied actions (e.g., ec2:StartInstances on a specific instance). Policies are JSON documents that bundle permissions and are attached to users, groups, or roles. Each statement says Effect (Allow/Deny), Action (API calls), and Resource (ARNs). When a request arrives, IAM evaluates all applicable policies: an explicit Deny always wins; otherwise the request needs an explicit Allow. Policy types: AWS managed (prebuilt by AWS, e.g., ReadOnlyAccess), customer managed (your own reusable policies), and inline (embedded in one identity).

5. What is the least privilege principle? Why is it important in cloud security?

Least privilege means granting every identity only the minimum permissions required to do its task — nothing more. It is important because credentials get leaked, phished, or misused; if a compromised key only had read access to one service, the attacker cannot spin up expensive resources, delete data, or move laterally. Most cloud breaches and surprise bills trace back to over-permissioned identities, so least privilege is the single most effective habit in cloud security.

6. What is MFA (Multi-Factor Authentication) and how does it enhance account security?

MFA requires two or more independent factors to sign in — typically something you know (password) plus something you have (a time-based code from an authenticator app or hardware key). It enhances security because a stolen password alone is no longer enough: the attacker would also need the victim’s phone or hardware token, which defeats the most common attack, credential theft/phishing. MFA is strongly recommended on the root account and all privileged IAM users, and can be enforced with IAM policy conditions.

7. Differences between Admin, Read-only, and custom roles in IAM.

Admin (AdministratorAccess): full control — can use every service and perform every action, including managing users and billing. Reserved for a tiny number of trusted identities.

Read-only (ReadOnlyAccess): can view, list, and describe resources across services but cannot create, modify, or delete anything — ideal for auditors, trainees, and monitoring.

Custom roles/policies: hand-written JSON granting exactly the actions the workload needs (e.g., only ec2:Describe* on specific instances). Most work, most precise, and the correct way to implement least privilege — used in this lab to build a minimal EC2 read-only role.

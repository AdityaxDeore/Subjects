Introduction to UML Activity Diagrams

An Activity Diagram is a behavioral diagram within the Unified Modeling Language (UML) specification that portrays the step-by-step workflow of stepwise activities and actions with support for choice, iteration, and concurrency. In software engineering, activity diagrams represent both computational workflows and organizational business processes, functioning as advanced object-oriented flowcharts.

Unlike standard functional flowcharts, UML Activity Diagrams provide native constructs for:

  • Swimlanes (Activity Partitions): Allocating responsibilities among distinct actors, subsystems, or computing tiers.
  • Concurrency (Forks & Joins): Specifying threads of execution that execute in parallel and later synchronize.
  • Object Flows: Illustrating how physical artifacts or digital data tokens flow between and are transformed by operational activities.

UML 2.0 Activity Diagram Notations & Standards

UML 2.0 standardizes symbols to describe system dynamics, data transformations, and decision paths without ambiguity:

Notation Element Graphical Symbol Description & Behavioral Semantics
Initial Node Solid black circle (⚫) Marks the commencement of an activity invocation when the process begins.
Action / Activity Rounded Rectangle Represents an atomic, non-interruptible step or functional sub-process.
Decision Node Diamond (◇) with guards Evaluates conditional guards (e.g., [Yes] / [No]) to route a single input into mutually exclusive outputs.
Merge Node Diamond (◇) with 2+ inputs Unifies multiple alternative paths into a single output stream without synchronization.
Fork Node Thick horizontal / vertical bar Splits a single incoming control flow into two or more concurrently executing parallel flows.
Join Node Thick horizontal / vertical bar Synchronizes multiple concurrent control flows; waits for all incoming flows before yielding control.
Object Node Rectangle with stereotype Represents an instance of data or physical resource (e.g., «object: WasteBatch») generated or consumed.
Activity Final Node Bullseye Circle (◉) Terminates all control and object flows across all concurrent threads in the activity.
Swimlane / Partition Vertical or Horizontal Columns Organizes responsibilities across organizational boundaries, actors, microservices, or devices.

Mathematical Flow Representation

In Petri-net semantics underlying UML 2.0 Activity Graphs, an activity state transition is triggered when token condition \(T_c\) is satisfied across all incoming edges \(E_{in}\):

\[ T_c = \bigwedge_{e \in E_{in}} \text{HasToken}(e) \implies \text{FireAction}(A) \implies \forall e' \in E_{out}, \text{EmitToken}(e') \]

For Decision nodes, routing satisfies the condition of mutually exclusive guard predicates:

\[ \sum_{i=1}^{n} P(\text{Guard}_i) = 1 \quad \text{where} \quad \text{Guard}_j \cap \text{Guard}_k = \emptyset \quad (\forall j \neq k) \]

Open Ocean Cleanup System Architecture

The Open Ocean Cleanup system is an autonomous cyber-physical marine restoration platform designed to detect, intercept, collect, and recycle marine plastics (macro-plastics, derelict ghost fishing nets, and surface microplastics) while ensuring zero harm to marine biodiversity. The system workflow is architected across four distinct Swimlanes:

Partition 1: Operator / Player (Command & Telemetry)

Represents the human operator or gamer initiating missions, selecting ocean sectors (e.g., Great Pacific Garbage Patch, North Atlantic Gyre), tracking live vessel metrics, managing fuel/storage economics, and receiving tokenized ecological rewards.

Partition 2: Navigation & Detection System (Autonomous Edge AI)

Executes pathfinding algorithms, obstacle detection, and edge neural network inference. It interfaces with onboard multi-spectral cameras, high-frequency forward sonar, and LiDAR to scan ocean surfaces and classify floating entities into marine debris, navigational hazards, or living marine fauna.

Partition 3: Cleanup & Collection Unit (Robotic Ingestion)

Operates the physical collection apparatus consisting of automated floating containment booms, a variable-speed perforated conveyor belt, bycatch escape gratings, hydraulic balers, and ultrasonic storage hopper sensors.

Partition 4: Base Harbor & Recycling Facility (Post-Mission Operations)

Oversees automated dock mooring, shore battery fast-charging, container crane offloading, Near-Infrared (NIR) polymer spectroscopic sorting (PET, HDPE, PP), pelletization, impact score computation, and ledger logging.

Operational Lifecycle: Five-Phase Execution Flow

The activity model coordinates the end-to-end mission cycle into five sequential yet concurrent phases:

Phase 1: Mission Setup & Pre-Launch Concurrent Diagnostics

The operator logs in, configures the vessel payload thresholds, and commits a designated ocean cleanup grid. The vessel performs pre-launch self-diagnostics. If any subsystem registers a fault, execution is routed to a maintenance sub-loop. Upon passing, a Fork Bar triggers three concurrent initializations: powering electric propulsion waterjets, calibrating sonar/camera sensors, and establishing encrypted telemetry with Harbor Command, joined via a Join Bar.

Phase 2: Ocean Patrol, Sensor Surveillance & Classification

The vessel enters an autonomous patrol loop across coordinate waypoints. Active sensors sweep the water column. When an object is detected, a deep-learning classifier evaluates the contact:

  • Navigational Hazard (Reef/Storm): Triggers an evasive path recalculation keeping a 500m safety perimeter before re-entering the patrol grid.
  • Marine Wildlife (Cetaceans, Sea Turtles): Triggers a directional low-frequency acoustic deterrent ping to safely guide animals away while maintaining course.
  • Plastic Debris / Target Waste: Transfers control flow to the Collection Unit.

Phase 3: Plastic Ingestion, Bycatch Screening & Compression

Containment booms deploy to channel debris toward the intake conveyor. A Fork Bar splits flow into simultaneous plastic capture and hydraulic water-straining with bycatch escape grates. Once joined, a hydraulic compactor compresses collected plastics into dense bales and logs batch mass into an «object: WasteBatch» node. Bin sensors evaluate storage capacity. If under 90%, patrol resumes; if full (or battery < 20%), return autopilot initiates.

Phase 4: Autonomous Harbor Return & Container Offloading

The vessel returns via fuel-optimized cruise vectors, transmits payload manifests, docks via laser telemetry, locks into shore power for fast charging, and offloads compressed bales via automated crane gantry.

Phase 5: Polymer Granulation, Carbon Metrics & Eco-Rewards

In the recycling facility, plastics undergo automated Near-Infrared (NIR) polymer sorting and granulation into recyclable resin flakes. The platform calculates total kilograms diverted, estimates ocean plastic footprint reduction, mints verified «object: CleanCredits» tokens to the operator's wallet, updates global fleet leaderboards, and logs records to the database.

Exception Handling & Edge Cases

Robust operational design requires explicit modeling of alternate paths and boundary failures:

  • Sensor Blindness / Communication Blackout: If ocean spray or satellite loss interrupts telemetry, the vessel switches to autonomous dead-reckoning and holds position until connection recovers.
  • Derelict Net Entanglement: If propeller rpm drops sharply, the system issues an automated emergency stop, attempts reverse thrust pulse, and alerts harbor support if clearing fails.
  • Wildlife False Positives: High-confidence image thresholds guarantee that live fauna are given maximum clearance via benign acoustic deterrents.

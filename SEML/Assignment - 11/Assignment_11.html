4. Theory: Software Testing & JUnit 5 Architecture

Software testing is an indispensable verification activity in the Software Development Life Cycle (SDLC). Unit testing specifically isolates the smallest testable units of software (methods, classes, and cohesive modules) to validate that their actual runtime behavior complies precisely with specified requirements.

4.1 The Three-Tier Architecture of JUnit 5

Unlike legacy JUnit 4 which coupled runner, assertion, and discovery mechanisms into a single monolithic JAR, JUnit 5 is architected as three distinct, decoupled sub-projects:

  • JUnit Platform: Acts as the underlying foundation for launching testing frameworks on the JVM. It defines the formal TestEngine API for discovering and running tests, provides command-line console launchers, and exposes discovery hooks for IDEs (IntelliJ IDEA, Eclipse, VS Code) and build automation tools (Apache Maven, Gradle).
  • JUnit Jupiter: The combination of the new programming model and extension model for authoring tests in JUnit 5. It contains junit-jupiter-api (defining annotations, assertions, and assumptions), junit-jupiter-engine (the execution core), and junit-jupiter-params (for parameterized data feeds).
  • JUnit Vintage: Provides backward compatibility by hosting a specialized TestEngine capable of executing legacy JUnit 3 and JUnit 4 test suites seamlessly alongside modern Jupiter tests.
Figure 2: JUnit 5 Decoupled Three-Tier Architecture (Client Tier, Platform, Engines)
Architectural Advantage of JUnit 5: By separating the Platform (runner/discovery) from Jupiter (test authoring API), tool vendors only need to support the Platform API once. Multiple test engines (Jupiter, Vintage, Spock, Cucumber) can run concurrently under a unified reporting pipeline.

5. JUnit 5 Method Lifecycle & Instance Isolation

To prevent side-effects, mutable state leakage, and order-dependent flaky tests, JUnit 5 enforces strict test isolation. By default, JUnit constructs a brand new instance of the test class prior to executing each individual @Test method (TestInstance.Lifecycle.PER_METHOD).

Figure 3: JUnit 5 Execution Lifecycle and Instance Isolation Workflow

5.1 Lifecycle Execution Phases

Phase JUnit 5 Annotation Operational Behavior & Purpose
Class Initialization @BeforeAll (static) Executes once before any test methods run. Ideal for heavy shared fixtures (database spin-up, container init).
Method Setup @BeforeEach Executes immediately before each test. Instantiates fresh domain entities (e.g., fresh Player and services).
Test Execution @Test / @ParameterizedTest The core test logic containing method invocations and assertions (e.g., assertAll, assertThrows).
Method Teardown @AfterEach Executes immediately after each test. Resets mocks, clears temporary collections, and prevents memory leaks.
Class Teardown @AfterAll (static) Executes once after all tests in the class finish. Closes server connections and releases global resources.
Mathematical Reliability Guarantee of JUnit 5 Isolation:
Let \(S_i\) denote the system state before test \(T_i\). Under PER_METHOD isolation with clean @BeforeEach fixtures, the pre-state is strictly invariant: \(S_i = S_0\) for all \(i \in \{1, \dots, n\}\). Consequently, the conditional probability of test interference is zero: \(P( ext{Fail}(T_j) \mid ext{Pass}(T_i)) = P( ext{Fail}(T_j))\).

6. Concepts & Annotations Used in JUnit 5

JUnit 5 provides an extensive suite of expressive annotations and assertion primitives tailored for modern object-oriented quality assurance.

Annotation Scope Functional Semantics & OceanCleanup Usage
@Test Method Marks standard automated unit tests. Package-private visibility permitted.
@DisplayName("...") Class / Method Provides descriptive human-readable test names in IDEs and Surefire reports.
@ParameterizedTest Method Executes the same test method multiple times with differing arguments.

@Disabled("...") Class / Method Skips execution with technical explanation (used for future v3.0 micro-banking).
@Timeout(val, unit) Class / Method Fails if execution exceeds time threshold (e.g., 100,000 tick updates < 1s).
@Suite Master Class Discovers and executes all 6 service test classes under a unified test run.

6.1 Modern JUnit 5 Assertion Mechanisms

  • Grouped Assertions (assertAll): Groups assertions inside lambda executables. Unlike JUnit 4 where the first failed assertion aborts remaining checks, assertAll evaluates every assertion and reports all failures simultaneously.
  • Exception Assertions (assertThrows): Validates that executing code throws an expected exception type, returning the exception instance for message and causal inspection: assertThrows(InventoryFullException.class, () -> service.collectTrash(player, extraItem));
  • Preemptive Timeouts (assertTimeoutPreemptively): Guarantees that runaway infinite loops or blocked threads are forcefully terminated once the stipulated duration elapsed.

@Nested
@DisplayName("Nested Tests: Upgrade Logic and Boundary Scenarios")
class UpgradeBoundaryTests {
    @Test
    @DisplayName("Should prevent upgrade when player collects fewer trash than required")
    void testUpgradeFailsWithInsufficientTrash() {
        for (int i = 0; i < 4; i++) player.addTrash(new TrashItem("t_" + i, TrashItem.TrashType.PLASTIC_BOTTLE, i, i));
        assertThrows(IllegalStateException.class, () -> boatService.upgradeBoat(player));
        assertEquals(1, player.getBoatLevel());
    }

    @Test
    @DisplayName("Should throw MaxLevelReachedException when upgrading beyond Level 4")
    void testMaxLevelBoundary() {
        player.setBoatLevel(4);
        assertThrows(MaxLevelReachedException.class, () -> boatService.upgradeBoat(player));
    }
}
EconomyAndRecyclingServiceTest.java — Repeated Tests & Disabled Features JUnit Jupiter 
@Test
@DisplayName("Should throw InsufficientFundsException when player lacks 15 gold for food")
void testPurchaseFoodThrowsInsufficientFunds() {
    player.addGold(14); // Exactly 1 gold below required 15 threshold
    player.setEnergy(50.0);

    InsufficientFundsException ex = assertThrows(InsufficientFundsException.class, () ->
        economyService.purchaseFood(player)
    );
    assertTrue(ex.getMessage().contains("Insufficient gold"));
    assertEquals(14, player.getGold(), "Gold balance must remain untouched");
}

13. Conclusion & Key Learnings

In this assignment, an automated unit testing suite was successfully architected, implemented, and executed for the OceanCleanup2 simulation system using Java and JUnit 5. The practical findings and theoretical learnings include:

  • Three-Tier Decoupling: The architectural separation into JUnit Platform, JUnit Jupiter, and JUnit Vintage ensures clean separation between test authoring, parameterized data injection, and build-tool discovery.
  • Data-Driven Testing Efficiency: Utilizing @ParameterizedTest with @CsvSource, @EnumSource, and @ValueSource reduced boilerplate test code by over 65% while testing dozens of permutations of vessel speeds, capacities, litter point distributions, and marine species.
  • Boundary & Exception Containment: The assertThrows assertion ensured that invalid operations—such as inventory overflows (InventoryFullException), insufficient coin balances (InsufficientFundsException), and illegal state transitions (InvalidGameStateException)—are strictly prevented and safely contained.
  • Hierarchical Organization: BDD-style @Nested test classes allowed logical grouping of boundary and exception scenarios, producing clean, intuitive test hierarchies in reporting tools.
  • Zero Regression Verification: Running the complete 66-test suite via Maven Surefire confirmed a 100% active pass rate, proving that the underlying mathematical algorithms, state machine transitions, and economy equations behave deterministically under all normal, boundary, and failure scenarios.
